## 2026-08-13 — Student-persona walkthrough: a live rendering bug on every Tier 0 lesson, found by actually reading the pages

**Scope:** `components/ContentRenderer.tsx`, `lib/content/tier0/{hello,packages}.ts`. Found while doing a live, in-browser walkthrough of the whole site as a Python-fluent, Go-naive learner — not a code review, an attempt to actually use the product the way a visitor would, clicking, typing, and running the labs for real.

**The bug: `ContentRenderer` had two different rendering rules for prose, and content authors had no way to know which one they were using.** `"text"` blocks rendered through `dangerouslySetInnerHTML`, so a `<code>` or `<em>` tag in the source became real inline formatting. Every other block type — `"list"`, `"callout"`, and the four step-anatomy blocks (`pattern`, `requirement`, `constraint`, `breakIt`) plus `VerifyBlock` — rendered the same string through plain JSX interpolation, which React escapes by default. Nothing in the type system or the authoring pattern distinguished the two: `lib/content/tier0/*.ts` writes `<code>` and `<em>` into `callout` blocks exactly the way it writes them into `text` blocks, because from the content file there was no visible difference. The result, live: every one of the 14 Tier 0 lessons' "break it, deliberately" callout — the pedagogical payoff of the lesson — was showing its reader literal `<code>fmt.Println</code>` and `<em>"fmt" imported and not used</em>` instead of formatted text. Confirmed by reading the actual rendered page, not by inspecting the source; `/basics/hello` and `/basics/packages` were checked directly, and a grep for `<code>|<em>|<strong>|<a href` across `lib/content/tier0` found the pattern in all 14 files (65 occurrences). A third instance was caught live on `/orientation/learn-syntax`: a `list` block's items included `<code>&x</code>` and `<code>*p</code>`, rendering the same way.

**Fixed the component for every block type, not just the ones caught with content live in them.** `lib/content/projects` (the entire 11-project step curriculum — `pattern`/`requirement`/`constraint`/`verify`/`breakIt`) has zero current instances of embedded HTML, so those code paths were not live-broken today. Fixed them anyway: leaving five block types silently unable to render the exact same `<code>`/`<em>`/`<a>` markup that two sibling block types support is the same landmine that just went off in Tier 0, waiting for the next content author who reaches for a `<code>` tag in a `breakIt.why` or a `pattern.task` without knowing that one, unlike its neighbors, won't render it. Left `AssessmentBlock`'s `desiredOutput`/`desiredMetrics` fields alone deliberately: those render literal program output and metric text in a monospace block, and HTML-interpreting genuine program output would be a correctness regression in the other direction (stray `<`/`>` in real output should display, not be swallowed as a broken tag).

**Also fixed, not just found: two dead-end prose references to "the setup page."** `lib/content/tier0/hello.ts` (lesson 1) and `packages.ts` (lesson 14) both say "the setup page" with no link — text written on the assumption the reader arrived via Orientation's own sequence (which ends by pointing here), true only for readers who took that path. The homepage's own "New to Go? Start with Basics" CTA sends total beginners straight to `/basics`, skipping Orientation — including its step 4, "Install Go and run your first program," which is where `mkdir hello && cd hello && go mod init example/hello` actually happens. A reader who followed the homepage's own beginner CTA and started at lesson 1 would hit an instruction referencing a folder they were never told to create, with no link back. Fixed narrowly: `hello.ts` now links `/orientation/setup` and inlines the three commands as a fallback ("Haven't done that yet?"), so the lesson is self-sufficient regardless of entry path; `packages.ts`'s reference now links the same page. **Deliberately not changed:** the homepage CTA itself, and whether "New to Go?" should route through Orientation first. That's a real question — Orientation's own design is "the airlock before Tier 1" and Basics assumes it's already been through — but it's a positioning call on the redesign's carefully-built homepage, not a broken-reference bug, and redirecting a primary CTA unasked is a different kind of change than fixing a dead link. Raised as its own Open observation instead.

**Also verified working, which is worth recording since a review that only lists bugs looks like it wasn't checking the good paths:** the cli-renamer lab was actually built and run (`go run ./check` from `labs/cli-renamer`), and its live output matched the page's own predicted output exactly, scenario by scenario, including which of the 7 pass before any code is written. Progress tracking was exercised with a real click dispatch (not assumed from a prior session): a step marker toggle updated `localStorage`, the project's own step badge, in one round trip. Search was tried with a realistic panic query ("nil pointer panic," surfaced the typed-nil-interface failure lab specifically, not generic pointer results) and a real double-typo ("conncurency" → every concurrency failure lab plus the WaitGroup source walkthrough). Mobile drawer, theme toggle, and the nav's "Continue" persistence across non-tracked page types (concepts/failures/idioms) all confirmed via direct DOM/localStorage inspection after `computer` click actions proved unreliable in this environment (the Browser pane isn't visually displayed here, which breaks screenshot- and coordinate-based interaction — a `.click()` dispatch plus a state check in a separate tool call is the reliable substitute, confirmed by cross-checking against a case where the two methods agreed).

**Verification:** `npx tsc --noEmit`, `npm run lint` (`--max-warnings=0`), and `npm run build` all clean at the same page count after the `ContentRenderer` change, since it touches three page types (`basics/[slug]`, `projects/[slug]`, `orientation/[slug]`) at once. Every live fix re-checked in the browser post-edit: `/basics/hello`'s callout, `/basics/packages`'s closing callout and its new link, `/orientation/learn-syntax`'s list.

## 2026-08-09 — Search (fuse.js): the whole site, not just the two types the backlog named, and one entry that would have been silently missing

**Scope:** `lib/search-index.ts` (new), `components/SearchPalette.tsx` (new), `app/layout.tsx`, `components/Nav.tsx`. Adds `fuse.js` as a dependency (zero dependencies of its own). Ships Up Next #5, scoped wider than its literal wording.

**Scoped to every content type, not the two the backlog named.** Up Next #5 says "search across projects and concepts" — written before failure labs, idiom exercises, source walkthroughs, and Tier 0 existed as separate tracks. The reason the item exists at all — "the site is now large enough that browsing is slow" — applies exactly as much to a failure lab as to a project, so the index covers all six content types plus the capstone. Logged as a deliberate scope call, not a literal reading of the backlog line.

**The index is `{type, title, subtitle, href, tags}` only — never full content.** Project step bodies, concept prose, and failure-lab diagnosis HTML never enter it. That keeps ~120 records at a few hundred bytes each (~15KB uncompressed), trivial to pass server → client as a prop, and — the real reason — keeps every project's full lesson text and every concept's full explanation out of the search palette's client bundle, which is what would actually be heavy.

**The capstone is not an array, and it was missing on the first pass.** Every other content type is `Type[]`, mapped straight into records. `capstone` (`lib/capstone.ts`) is a single object — the one entity that doesn't fit the `.map()` pattern the rest of the file uses — and it was absent from the index until a manual search for "capstone" during browser verification came back empty. Added as a one-off literal entry, with a comment naming exactly why it needed one.

**Querying "capstone" still failed after adding the record, for an unrelated reason.** `capstone.name` is `"linkd"` and its tagline never uses the word "capstone" — so Fuse's fuzzy match against title/subtitle/tags had nothing close enough to match. The record's own `type` field ("Capstone", "Concept", "Failure lab", …) is metadata Fuse never looks at, not searchable text. Fixed generally, not as a one-off: every record's `type` is folded into its own `tags` array, so a type-name search ("capstone", "concept", "failure") works for all six categories, not patched only for the one that happened to get caught.

**The trigger is a real link's sibling, not a toggle-inside-toggle.** Learned from the mega menu's earlier bug in the same file (hover-open + click-toggle fighting each other): the search trigger is a plain button that only ever opens, with its own effect handling Escape/focus/scroll-lock while open. The ⌘K/Ctrl+K global listener is registered once, unconditionally, in its own effect — it has to outlive the panel to reopen it, unlike everything else.

**Query/selection reset on open moved out of the effect entirely, matching Nav's own pattern for closing on navigation.** The natural first draft called `setQuery("")` synchronously inside `useEffect(() => { if (!open) return; ... }, [open])`, which is a lint error (`react-hooks/set-state-in-effect`) for the same reason it was in Nav: reacting to a state change during render is not a sync with an external system. Split it: a render-time `wasOpen` comparison (identical shape to Nav's `lastPathname` trick) resets query/selection, and the effect keeps only genuine DOM work — focusing the input, locking `body.style.overflow`, subscribing to Escape.

**Verified end to end in the browser, including one deliberately wrong query.** Searched the typo "gorutine" and got four different content types back (a concept, an idiom exercise, a failure lab, three projects) — confirming cross-type fuzzy matching, not just an exact-title lookup. Arrow-key navigation, Enter-to-navigate (landed on `/concepts/scheduler`), Escape, and ⌘K toggle all exercised directly; the first ⌘K test produced a false negative from double-dispatching the same synthetic event in one test call, re-verified clean with a single dispatch. Contrast checked in both themes on the dialog's title, subtitle, type label, and input text — all pass AA. No horizontal overflow at 375px.

**`npm audit` surfaced 8 pre-existing vulnerabilities while installing `fuse.js`**, none of them from `fuse.js` itself (it has zero dependencies) — all transitive from `next`/`eslint` tooling. Not fixed here: `next` itself is in the high-severity list, so `npm audit fix` risks a Next.js version bump as an unrelated side effect of a search feature. Logged in ROADMAP as its own item for a deliberate pass.

## 2026-08-09 — Progress tracking (localStorage MVP): one flat id map, and a continue button that goes in the nav

**Scope:** `lib/progress.ts` (new), `lib/progress-ids.ts` (new), `components/{VisitTracker,ProgressBadge,StepMarker,LessonMarker}.tsx` (new), `app/page.tsx`, `app/basics/{page,[slug]/page}.tsx`, `app/projects/[slug]/page.tsx`, `components/Nav.tsx`. Ships Up Next #4 as specced: "no backend yet; just visible tier completion and a last-visited continue button."

**One flat map of ids, not separate step/lesson collections.** A step and a Tier 0 lesson are both just "a thing you can check off" from the UI's point of view, and a single namespaced id (`step:<project>:<n>`, `lesson:<slug>`) lets one function — `countDone(data, ids)` — answer "how many of these are done" for a single project's header, a whole tier's aggregate on the homepage, or one marker, without three separate code paths.

**Split into two modules over one, and it was not optional.** The store (`lib/progress.ts`) is `"use client"`, because it touches `localStorage` and `useSyncExternalStore`. The homepage and the basics index are server components that need to build id arrays — `stepId(project.slug, s.n)` — to hand to `<ProgressBadge>`. Calling a function from a `"use client"` module inside a server component is a Next.js **build error**, not a lint warning, and it was caught exactly that way: `npm run build` failed on `/` with "Attempted to call lessonId() from the server but lessonId is on the client." The fix is `lib/progress-ids.ts`, holding only the pure id builders and the `ProgressData` type — no React, no storage — importable from either side. `lib/progress.ts` re-exports them so client components can still pull everything from one path.

**State lives in a module-level external store, the same shape as `ThemeToggle`'s.** Progress has to be readable from components with no shared parent — the nav's CTA, a step marker three levels into a server-rendered tree — and a React context provider would mean wrapping the entire app in a client boundary for what is, in the end, one object synced to `localStorage`. `useSyncExternalStore`'s server snapshot is the empty state, so SSR and the first hydration pass always render "Start the path"; the real snapshot lands right after, the same swap `ThemeToggle` already does for its icon. No hydration mismatch, verified: the console stayed clean on load.

**The continue affordance is literally "last visited," not a guess at "where you meant to resume."** ROADMAP asked for a last-visited button, not a smart resume-to-next-incomplete-step, and the two are different features — a wrong guess at intent is worse than an honest link to the page you were last on. `VisitTracker` records `{href, label}` on mount of any project or basics-lesson page; the nav's primary CTA reads it and swaps from "Start the path →" to "Continue: `<label>` →" everywhere in the site, not just on the homepage, since the nav is the one element present on every page.

**One deliberate, disclosed reuse of an already-flagged color pair.** The step and lesson markers' "done" state uses the same `bg-m-accent`/`text-m-on-accent` fill as the primary button, which measures 3.76:1 in light mode — the exact pair already logged as below AA and parked for Aboturab's call. Considered inventing a different done-state color to dodge it, and didn't: that would leave the site with two different answers to "accent fill, light label" instead of one flagged one, and whatever fix lands for the button now fixes all three uses at once. Noted in the existing ROADMAP entry rather than opened as a new one.

**Verified in the browser, not just built:** cleared `localStorage`, confirmed "Start the path" on a cold load, clicked a step marker and watched the project's own badge, the homepage tier badge, and the nav CTA all update from the same click with no reload — that's the actual claim (one store, many readers), not just that each piece renders. Marked a basics lesson complete and confirmed the index page shows a checkmark instead of its order number. tsc, lint, and build clean at 124 pages.

## 2026-08-09 — Redesign, third pass: migrating the whole site through the token layer, and making a 15,000px page navigable

**Scope:** `app/globals.css`, `tailwind.config.ts`, `app/projects/[slug]`, `app/source/[slug]`, `components/{ProjectSection,GoCode,PageNav,ReadingProgress}`, `app/{basics,concepts}/[slug]`. No content modules, no copy, no validate contract.

**The migration was done at the token layer, not by editing pages.** A count first: roughly a thousand utility uses across twenty-odd files — `go-cyan` ×100, `text-muted` ×164, `text-foreground` ×112, `border-border` ×80, `rounded*` ×109, `font-serif` ×29. Rewriting those by hand is a large diff with a large chance of missing some. Instead the original semantic tokens now *alias* the Modernist ones, and two Tailwind scales were repointed: `sans` and `serif` both resolve to Archivo (so the 29 serif headings convert untouched, and the critique's "three families read as three different sites" is fixed everywhere rather than only on the homepage), and the whole `borderRadius` scale is 0 (the system's "do not round a corner anywhere"). Verified on a project page afterwards: only Archivo and JetBrains Mono in use, zero rounded elements, modernist ground and accent throughout.

**The three Go brand colours collapse to one role**, which is what a mono scheme means. They resolve to **accent-700, not the raw accent**, because 48 of their ~210 uses are `text-go-cyan` on small labels where the raw accent measures 3.76:1 and fails AA. Tier differentiation is no loss: the labels already say "Tier 01/02/03", and the redesigned homepage had already put all three tiers in one colour.

**Syntax highlighting was retuned, not stripped.** The obvious reading of a mono system is that code goes ink-and-one-accent, which is what the homepage hero does. That is wrong for the rest of the site: the handoff itself keeps a monospace face because code is "functional, not decorative", and by exactly that reasoning the colour separating a string from a comment on a site that teaches Go is carrying information. Kept eight distinct token colours drawn from the accent ramp and neutrals, separated by value where they cannot be separated by hue. All eight measured against the code surface in both themes.

**One real contrast miss, found by measuring rather than assuming:** `--sx-comment` at `#6f6c6c` came in at **4.29:1** against the code block's own surface (`#eae9e9`, darker than the page ground it was chosen against). On the source-reading walkthroughs the comments are the standard library's own and are the thing being taught — content, not chrome — so it moved to `#686565`, 4.76:1, still a step lighter than `--sx-punct` so the two stay apart.

**Contrast sweeps needed two corrections before they meant anything.** The first pass reported failures at 2.02:1 that were not real: `bg-go-cyan/5` is a 5% *tint*, and treating the nearest painted layer as opaque ignores everything behind it, so the sweep now composites the full background stack. The second pass reported failures at ~1.00:1 — foreground equal to background — which is the signature of a colour pinned mid-transition, because toggling `.dark` in a pane that composites no frames leaves `getComputedStyle` returning the old value. Settling animations first fixed it. With both corrected: **zero failures across the homepage, project, concept, capstone, failure and source pages in both themes.**

**A project page is ~15,000px — about seventeen screens.** That was the actual complaint, and it is a navigation problem, not a prose problem. Three things:

- **`PageNav`**, a sticky contents rail at `xl` and up, built from what the page actually renders (a project with no constraints section gets no orphan entry). It tracks the section you are *in* rather than the one you last clicked, so it doubles as a position indicator. Active section is "the last one whose top has passed a reading line", not "topmost visible" — the latter flickers backwards whenever a tall block scrolls through, and "most visible" sits on a long step while its successor fills the screen. Added to project pages and to source walkthroughs (~10,700px, twelve screens).
- **`ReadingProgress`**, drawn into the nav's existing 2px bottom rule rather than added as a new bar. The divider already spans the viewport; filling it with the accent answers "how much is left" without introducing an element the system would have to justify.
- **A single spine behind the step markers**, so ten steps read as one run of work rather than ten unrelated blocks, plus scroll entrances per step.

**Verified:** tsc, lint (`--max-warnings=0`), validate and build clean at 124 pages; every rail anchor resolves to a real element on both page types; no horizontal overflow; all thirteen page types return 200.

## 2026-08-09 — Redesign, second pass: the mega menu's dead strip, and giving a flat system somewhere to move

**Scope:** `app/page.tsx`, `app/globals.css`, `app/layout.tsx`, `components/Nav.tsx`, `components/Motion.tsx` (new). No content changes, no copy changes, no other page.

**Why.** Aboturab's read of the first pass: cramped, static, and the mega menu unusable — "it disappears" when you try to move into it. All three are fair, and the first is a real bug rather than taste.

**The mega menu had a dead strip.** The panel hangs below the whole nav bar, but the trigger's hover box ends with the word "Projects" — measured on the running page, the trigger's box ended at y=45 and the panel began at y=66. ## 2026-08-06 — One-Stop Phase 8: the capstone, and proving a suite can fail

**Scope:** `labs/capstone/` (new module: SPEC.md, starter, reference, suite, slo, seed, internal/harness, internal/conform, check.sh), `labs/check.sh` hook, `lib/content.ts` capstone types, `lib/content/capstone.ts`, `lib/capstone.ts`, `app/capstone/page.tsx`, `components/Nav.tsx`, `scripts/validate.ts`, `eslint.config.mjs`.

**The spec: `linkd`, a link shortener.** The brief offered "URL shortener or link tracker with auth, rate limiting, persistence, metrics" and said to log the choice. Took the shortener because its shape maximises what a black-box suite can actually observe: a public redirect path that is trivially hammerable, an authenticated API with real owner isolation, a natural place for a per-token rate limit, a store whose contents must outlive the process, and a metrics endpoint that is the only reason goroutine leaks are visible from outside at all. `/metrics` carrying `runtime.NumGoroutine()` is a spec requirement rather than a convenience: without it, "does not leak" is unobservable and the phrase would be decoration.

**Zero guidance means the suite is a grader, not a mirror, and that is a deliberate reversal.** `labs/cli-renamer/check` opens by saying it "is a mirror, not a grader: the differences are simply the work left." That is right for T1 P1. It is wrong here, because the capstone's entire claim is that passing means something. So the capstone harness states thresholds, fails, and exits non-zero. The two tones are both intentional and they sit at opposite ends of the same path.

**Black-box was the constraint that made the rest honest.** Nothing in `suite`, `slo` or `seed` reads the submission's source. They compile the package, run the binary, and speak HTTP. That keeps "any layout that meets the spec passes" literally true, and it forced every requirement in SPEC.md to be one that can be observed from outside. Two requirements were rewritten during the build because they could not be: an early draft required work to stop when a client disconnects, which needs a route slow enough to abandon and this spec has none, and an early durability clause promised more than a kill test can check.

**The seeded-bug harness is the actual deliverable.** The brief's done-when is "a reference implementation passes suite + SLOs, and the suite catches seeded bugs from the Phase 5 failure classes." A suite that has only ever been run against correct code has not been tested, it has been agreed with. `go run ./seed` copies the reference into a throwaway module, applies one named bug, compiles it, and runs exactly the checks that bug is supposed to trip. Eleven seeds, all caught. Three failure modes are kept apart on purpose because they mean different things: `stale` (the code the seed patches has moved, so the bug was never introduced), `broken` (the patched code does not compile, so nothing was proven), and `missed` (the bug went in, it built, and the suite passed anyway). Only the last is a hole in the suite; treating either of the first two as a pass is how a harness rots into decoration. This paid off within the session: refactoring the store moved the code the `data-race` seed patches, and the prover said `stale` rather than quietly passing.

**A lost update is not observable from outside a service, and the first seed proved it.** The original `data-race` seed removed the lock from click counting; the check fired 250 concurrent redirects at one link and required exactly 250 clicks. It passed, consistently, across repeated runs. The arithmetic is why: 250 increments spread across milliseconds of HTTP overhead essentially never land in the same two-nanosecond window, so nothing is ever lost. Moving the race to an unlocked map read did not help either, for the same reason. What works is removing the lock from the write path, where a map being iterated for a snapshot is wide open for as long as the iteration takes: the Go runtime detects it and stops the process, which from outside looks like every connection dropping at once. Verified 6/6 runs before trusting it. The near-miss version, `concurrency/one-winner-per-alias`, catches the same seed only about half the time and was deliberately left out of the seed's `Catches` list, because a seed that fires intermittently is worse than no seed. **This is now taught on the page rather than hidden**: the suite never sees a race, it sees the wrong numbers a race eventually produces, and it is entirely possible to have the race and never see the numbers.

**Six failure classes have no seed, and the reasons ship.** `ctx-ignored` (no route slow enough to cancel), `defer-in-loop` (needs a descriptor metric that would exist only for the test), `loop-capture` (Go 1.22 gave each iteration its own variable), `mutex-by-value` (`go vet` catches a copied lock first, which is the right place), `slice-aliasing` (invisible once the response is serialised), `wg-add-after-wait` (covered by the process contract). validate.ts enforces that every one of the 15 classes appears in exactly one of the two lists and that nothing appears in both, so the page's accounting cannot quietly become partial.

**The SLO harness caught an O(n²) write path in my own reference, which is the best evidence it works.** First run: p99 209ms against a 50ms threshold. The cause was not fsync (removing it only moved p99 to 124ms) but the store rewriting the entire file on every create while holding the save lock, so a burst of N creates cost N full rewrites, each longer than the last. Fixed with group commit: the first caller in takes a snapshot and writes it, and everyone who mutated before that snapshot finds their sequence already saved and writes nothing. One disk write satisfies any number of waiting callers, which is the trade a database makes when it batches commits into one fsync. Result: p99 209ms → 16.0ms, throughput 10,891 → 24,174 req/s, with fsync kept. Thresholds were then set from that measurement with headroom (p99 50ms, 1,500 req/s), and the pre-fix implementation fails them, which is what makes them thresholds rather than decoration.

**Measured the instrument, not just the service.** The latency distribution came back with p50 of `0s`, which is impossible when the mean is ~4.5ms. A direct probe found this machine's monotonic clock has ~525µs granularity: 199,998 of 200,000 back-to-back `time.Now()` calls return an identical value. So `slo` now measures that granularity at startup and prints it when it is coarse, and says which percentile carries weight. A p50 of `0s` is the instrument, not the service, and printing it without that note would have been publishing a number I knew to be meaningless.

**Two checks were passing for the wrong reason and were fixed.** `startup/requires-tokens` and `startup/refuses-corrupt-store` both passed against `./starter`, a binary that does nothing but exit 1. A check that cannot tell correct refusal from total failure is not evidence, so both now run a positive control first: prove the target serves at all, then require it to refuse the bad input. Found by pointing the suite at the empty starter, which is exactly the kind of run worth doing before believing a green board.

**Windows cannot deliver the shutdown signal, and the skip says so on its own line.** `shutdown/drains-and-exits-zero` needs `SIGINT`/`SIGTERM` to a child process. It skips on Windows and prints why, matching the Phase 7 posture: a silent skip reads exactly like a pass. The durability checks are cross-platform because they kill the process outright, which also made the spec more precise (structural writes write-through, clicks batched to at most one second of loss) than the graceful-shutdown-only version it replaced.

**Drive-by: the lint gate was red for reasons unrelated to any change.** `eslint .` walked into a stale git worktree under `.claude/` and linted its `.next` build output, producing 23 errors in generated code. The inherited ignores only cover build output at the repo root. Added `**/.next/**`, `**/node_modules/**` and `.claude/**` to the flat config. Deliberately small and taken here rather than deferred, because the previous entry in this log exists to repair this same gate, and a gate that goes red for unrelated reasons is one people learn to ignore.

**Pedagogy rules:** all five held. Rule 3 (T3 hard-gated by benchmarks) is honoured and extended: the capstone carries four measurable objectives, each printed with its measurement and its margin. Rule 4 is untouched, since the capstone gates nothing. Rules 1, 2 and 5 are unaffected: no assessments moved, no anchor changed.

## 2026-07-25 — One-Stop Phase 7: guided source reading, and quoting code we did not write

**Scope:** the brief's Phase 7, complete. Five walkthroughs at `/source` (errors, bytes.Buffer, sync.WaitGroup, context, the net/http accept loop), 30 annotated excerpts, one find-it exercise each, a `SourceWalkthrough` content type with a validate.ts contract, `labs/source/check.sh` as the gate, and reverse links onto 24 concept pages and 8 project pages.

And the memory model does not make racy programs arbitrarily undefined: word-sized reads must observe some value actually written, with out-of-thin-air values forbidden, while multiword values (maps, slices, strings, interfaces) may be torn, and *that* is what the spec says can lead to arbitrary memory corruption. The distinction is the concept's third retrieval prompt.

**Sources:** go.dev/ref/mem and go.dev/doc/articles/race_detector (report shape, overhead, platform list), plus `go doc` on the local toolchain for `net/http.Server.Shutdown`/`Close`/`ErrServerClosed`/`RegisterOnShutdown` and `log/slog.Level`, whose gap-of-4 rationale is quoted from there.

## 2026-05-13 — Switch from sprint-based to continuous-improvement mode

**Decision:** Each agent now operates with a **standing brief** in addition to assigned tasks. When no task is assigned, the agent runs the brief — engineer does routine quality work, content runs persona walkthroughs and audience audits, PM monitors project health and ecosystem signals. The team works as a real product team would: continuous, self-driven, no waiting for tickets.

**Why:** Sprint-based work is bounded by what's been ticketed, which means the project only improves at the rate someone files tickets. Aboturab wants the team to think — see the site as a user, find friction, propose improvements, and ship them. The goal isn't "complete the backlog," it's "keep making this better until it's as good as it can be."

**Alternatives considered:** Keep pure sprint model; have each agent invent its own loop without explicit briefs; only PM has the standing brief.

**Logged by:** Aboturab + Claude Code
